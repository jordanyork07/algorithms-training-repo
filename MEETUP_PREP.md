# Interview Day Prep

This file is meant to match the real interview context and reduce avoidable stress on the day.

## Before the meeting
- Test the microphone, camera, and internet connection
- Open the IDE and confirm you can type and run code smoothly
- Keep a blank file ready before the call starts
- Have a second tab open with a quick reference for syntax or docs if needed
- Do not over-prepare by memorizing a solution; instead, rehearse the conversation flow

## During the call
- Introduce yourself briefly and be calm
- Start by restating the problem in your own words
- Ask a clarifying question if the question is ambiguous
- Talk through the brute-force idea before optimising
- Explain what you are checking, even if you are not completely sure yet
- State complexity before coding if possible
- Keep the code clean and easy to follow
- Validate obvious edge cases near the end

## What the interviewer is likely evaluating
1. Can you recognise the underlying structure of the problem?
2. Can you break a hard problem into simpler subproblems?
3. Can you explain your reasoning clearly?
4. Can you produce a reliable and readable solution in time?

## What to avoid
- Staying silent for long periods without explaining your thinking
- Jumping immediately into code without identifying the pattern
- Over-optimizing before checking the simplest correct approach
- Getting lost in minor implementation details without verifying the core logic

## Good default phrases
- “I’m going to restate the problem to make sure I understand the contract.”
- “I can see a brute-force approach, and I’m looking for the bottleneck.”
- “This seems like a pattern where we maintain a running invariant as we move through the data.”
- “I’m checking whether the answer space has a monotonic property, which would suggest binary search.”
- “I’d like to test one edge case before I finish.”
